Aiced Revision Panel: What Happened

Plain-English notes for explaining why the “Revised by Aiced” panel disappeared, and how it was fixed.

The short answer: This was not an AI, database, or CSS problem. One JavaScript variable had the wrong name. The page successfully began drawing the Original article, then JavaScript stopped before it could draw the Revised by Aiced panel.

What the user was supposed to see

Ask Aiced for a revision ↓ Flask asks AI for a proposed change ↓ Flask validates the proposal but does not save it yet ↓ Browser displays: Left: Original article Right: Revised by Aiced ↓ User chooses Accept Changes or Discard

What actually happened

  1. The AI revision request succeeded.
  2. The browser received the current article and the proposed revision.
  3. The browser started rendering the left-side Original article.
  4. It then calculated which article blocks had changed.
  5. That calculation referenced proposedBlocks, but the code had created the variable as revisedBlocks.
  6. JavaScript stopped at that point, before it appended the right-side Revised by Aiced panel.

This is why the left panel could still appear while the right panel was missing. The failure happened in the middle of rendering, not before rendering began.

The exact technical bug

The comparison renderer created:

const revisedBlocks = revisedArticle.contentBlocks || [];

But it later attempted to use:

proposedBlocks[proposedIndex]

Because proposedBlocks did not exist, the browser raised a JavaScript reference error. The correction was simply to use:

revisedBlocks[proposedIndex]

Why it was confusing

  • The visual symptom looked like a CSS/layout issue.
  • The server returned successful responses, so Flask logs looked normal.
  • The Original side rendered before the crash, making it seem like only the right column had a styling problem.
  • The review feature involves several steps: AI response, validation, temporary browser state, comparison logic, and the final page update.

What was improved beyond the one-line fix

  • A dedicated pendingArticleRevision view model now holds the current article, proposed article, and changed fields.
  • Normal article rendering and pending-comparison rendering are now separate paths. A normal rerender cannot accidentally overwrite a pending comparison.
  • Article revisions keep the side-by-side Original / Revised by Aiced comparison visible.
  • CTA-only, Campaign-only, and Audience-only revisions explicitly say that the article is unchanged, instead of showing a misleading article comparison.
  • Accept still uses the existing save workflow. Discard still makes no database change. Publishing and sending remain separate human actions.

How the fix was tested

  • Content-block article revision: both columns appear.
  • Title-only article revision: both columns appear.
  • CTA-only revision: a non-article review notice appears.
  • Discard: removes the pending comparison and restores the normal article.
  • Accept before saving a draft: applies the accepted revision to the browser proposal.
  • Rerendering while a revision is pending: keeps exactly one Revised by Aiced panel visible.

Useful analogy

Imagine two people setting up a before-and-after display. The first person puts the “before” page on the wall. The second person is supposed to hang the “after” page, but their instruction sheet refers to a tool name that does not exist. They stop immediately. The first page is still on the wall, but the second never gets hung.

Scope: frontend revision display only. No database schema, AI prompt, publishing, recipient selection, or email-sending behavior was changed.
